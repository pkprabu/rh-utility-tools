What is this app?

The Red Hat Email Auditor is a browser-based quality assurance tool for HTML email campaigns. It analyses the source code of an email before it is sent, automatically detecting a wide range of problems — from broken links and missing tracking parameters to brand guideline violations and email-client compatibility issues.

Think of it as a spell-checker, but for HTML email code. Just as a spell-checker scans a document for spelling mistakes before you publish it, the Email Auditor scans your email's HTML for technical, brand, and deliverability problems before you send it to thousands of recipients.

💡 Completely private. The app runs entirely inside your browser. Your HTML code is never uploaded to any server. No internet connection is required once the page has loaded.

Who should use it?

✍️

Email Developers

Validate HTML structure, CSS compatibility, and link integrity before handing off to campaign managers.

📢

Campaign Managers

Verify that tracking parameters (sc_cid) are correctly applied to every link before scheduling a send.

🎨

Brand Teams

Ensure font families, link colours, trademark symbols, and "Red Hat" spacing all conform to brand standards.

⚖️

Legal & Compliance

Confirm every email contains the legally required unsubscribe link and physical postal address (CAN-SPAM / GDPR).

Why is it needed?

HTML email is one of the most fragile environments in web development. Unlike a website that runs in a single controlled browser, an HTML email is rendered by dozens of different email clients — Gmail, Outlook, Apple Mail, Samsung Mail, Yahoo Mail — each with its own quirks, CSS restrictions, and rendering engines. A feature that works perfectly in one client can be completely broken in another.

The problems it prevents

1

Broken tracking — lost campaign data

Every marketing link must carry an sc_cid tracking parameter so that your analytics platform can attribute clicks to the correct campaign. A single link without it means you cannot measure that email's performance. With hundreds of links across dozens of campaigns, manual checking is error-prone and time-consuming.

2

Email client rendering failures

Outlook (used by the majority of enterprise organisations) does not support CSS Flexbox, Grid, animations, or transitions. Gmail strips <style> blocks and requires all CSS to be inline. Using any of these unsupported features means your email layout silently breaks for a large portion of your audience.

3

Legal non-compliance

CAN-SPAM (US) and GDPR (EU) legally require every commercial email to include a visible unsubscribe mechanism and a physical postal address. Missing either can result in regulatory fines. These are easy to overlook when a template is modified or content is updated.

4

Brand guideline violations

Red Hat's brand guidelines specify exact fonts (Red Hat Text, Red Hat Display), exact link colours (#EE0000 red, #0066CC blue), and exact trademark formatting — the registered trademark symbol must be written as <sup style="line-height:0;">®</sup>. Manual review across a team of multiple developers is inconsistent and unreliable.

5

Security vulnerabilities

Email clients block JavaScript entirely. An email containing <script> tags or inline event handlers (onclick, onload) will be rejected by spam filters and may flag the sender's domain as a security risk. Iframes and forms are equally problematic.

6

Gmail clipping

Gmail truncates emails larger than 102 KB with a "Message clipped" notice, hiding the unsubscribe link from the user — a direct CAN-SPAM violation. The auditor warns when your email approaches this threshold.

Business impact

The cost of an error in a sent email is significantly higher than the cost of catching it before sending. Unlike a website where you can push a hotfix, a sent email cannot be recalled.

📊

Accurate campaign attribution

Every click correctly attributed to its campaign means marketing decisions are based on real data. A missing sc_cid on even one high-traffic link can skew ROI calculations for the entire campaign.

🔒

Consistent brand trust

Recipients notice broken layouts, incorrect fonts, and misspelled brand names. Consistent, polished emails build trust. A single email with "RedHat" (one word) instead of "Red Hat" (two words) undermines brand credibility.

⚡

Reduced QA cycle time

A full manual audit of a complex HTML email takes 30–60 minutes per developer. The auditor completes the same check in under 3 seconds, freeing the team for higher-value work.

🛡️

Legal protection

Automated compliance checks for unsubscribe links and physical addresses reduce the risk of CAN-SPAM violations. Documentation that you ran pre-send QA provides a defensible paper trail.

Requirements

The Email Auditor has no installation requirements. It is a static HTML page that runs entirely in a modern web browser.

Browser support

  • Google Chrome 90+ — recommended (best compatibility)
  • Mozilla Firefox 90+ — fully supported
  • Microsoft Edge 90+ — fully supported
  • Apple Safari 15+ — fully supported

Internet connection

An internet connection is required only for the initial page load to fetch Bootstrap CSS, Red Hat fonts, and the jsPDF library from CDN. Once loaded, the audit itself runs 100% offline. If you open the tool and immediately disconnect from the internet, it will continue to function correctly.

⚠ File type restriction: The file upload feature accepts only .html and .htm files. Attempting to upload a Word document, PDF, or plain text file will produce an error.

How to use it

Using the auditor takes less than 30 seconds once you have your email's HTML code ready.

1

Enter the sc_cid value

In the top field labelled "Specific sc_cid Value", type the tracking code for this campaign — for example 7013a000003SUdXAAW. This unlocks the HTML input field below. The auditor uses this value to verify that every link in your email carries the correct tracking parameter.

2

Provide the HTML

There are three ways to provide your email's HTML:

  • Paste: Copy the HTML source from your email editor and paste it into the large text area.
  • Upload: Click the "Upload File" button and select your .html or .htm file.
  • Drag and drop: Drag an HTML file from your file manager and drop it directly onto the text area. A blue dashed border with a "Drop here" overlay will appear to confirm the drop zone is active.
3

Wait for results (automatic)

The audit runs automatically — there is no button to press. Results appear in the right panel within 1–3 seconds for typical emails. For very large files (over 200 KB) a "Auditing large file…" status message appears so you know the app is working.

4

Review and fix

Work through the results panel. Each item is colour-coded by severity. Click on any row in a failure table to highlight the corresponding element in the live preview (if the preview pane is open). Fix issues in your email editor, re-paste the updated HTML, and the audit runs again automatically.

5

Export the report

Once your review is complete, click "Export PDF" in the summary bar. A formatted PDF report is downloaded immediately to your computer. This report can be attached to your campaign ticket as evidence of pre-send QA.

Input modes

The auditor has two input modes, selected with the Full HTML / Body Only toggle above the text area.

Full HTML mode (default)

Use this when pasting or uploading a complete, standalone HTML email — one that starts with <!DOCTYPE html> and contains a full <html>, <head>, and <body> structure. This is the format produced by most email platforms (Marketo, HubSpot, Salesforce Marketing Cloud) when you export or view the email source.

In this mode the auditor checks for document-level issues: missing <meta charset>, missing <title>, missing viewport meta tag, and missing lang attribute.

Body Only mode

Use this when you only have the content of the email body — HTML that starts directly with a <table> or <div> without any surrounding document structure. The auditor automatically wraps the fragment in a minimal HTML shell before auditing it.

✅ When in doubt, use Full HTML mode. If your code contains <!DOCTYPE html> anywhere, use Full HTML mode. If it starts directly with a table or div, use Body Only mode.

Severity levels

Every check is classified into one of three severity levels. Understanding what each level means helps you prioritise your fixes.

LevelColourMeaningAction required?
Error Red A problem that will either break the email's functionality, violate a mandatory brand or legal requirement, or cause the email to fail QA. Errors must be fixed before the email is sent. Yes — block send
Warning Amber A best-practice violation or potential problem that may affect rendering in certain clients, readability, or accessibility. Should be fixed if possible, but may be acceptable depending on context. Investigate before sending
Info Blue A missing element that is recommended but not strictly mandatory. These flags bring items to your attention that some clients or contexts may require. Review and consider

A fourth state — Passed — means the check found no problems. A grey Disabled badge means the check has been turned off in the Settings panel and was not run.

🚨 The amber banner at the top of the page appears when any checks are disabled. If you see it, the audit results are incomplete. Click "Enable in Settings" to turn checks back on before treating the report as final.

Reading the results

Summary bar

At the top of the results panel you will see a row of coloured badges: N Errors N Warnings N Passed. These give you a quick overall health score at a glance. The Export PDF button is also here.

Accordion rows

Below the summary bar, every check has its own row in an accordion list. The row colour indicates the status:

  • Red row — this check found errors. Click the row to expand it and see a table of every failing item.
  • Amber row — this check found warnings. Click to expand.
  • Green row — this check passed. The row cannot be expanded (there is nothing to show).
  • Grey row — this check is disabled in Settings.

Element highlighting

For checks that involve specific HTML elements (images, tables, font failures, etc.), each row in the failure table is clickable. Clicking a row opens the live preview pane (if not already open) and draws a red outline around the exact element in your email that caused the failure. This makes it much faster to locate and fix the problem.

All checks — Errors

The following checks are classified as Errors. They represent mandatory requirements — the email must not be sent until all of these pass.

The same id="..." value used on multiple elements. IDs must be unique per document. Duplicates break anchor links and can cause unpredictable rendering.
Check nameWhat it detectsFix
HTML Structural Integrity Mismatched or unclosed HTML tags — e.g. <div> closed with </span>. These cause unpredictable layout breaks across email clients. Fix the mismatched tags in your HTML editor.
Malformed HTML Syntax Unclosed quote marks in attributes — e.g. href="https://example.com (missing closing quote). Browsers silently correct these but email clients may not. Close all attribute quotes correctly.
JavaScript Detected <script> tags or inline event handlers (onclick, onload, onmouseover) anywhere in the email. All JavaScript is stripped by email clients and the presence of script tags is a spam signal. Remove all script tags and event handler attributes.
Iframes Detected <iframe> elements. Blocked by all major email clients and considered a spam indicator. Remove all iframes. Use static images or links instead.
Form Elements Detected <form>, <input>, <select>, <textarea>, <button> elements. Forms are stripped or broken in virtually all email clients. Remove all form elements. Link to a landing page with a form instead.
Insecure Links (http://) Links using http:// instead of https://. Insecure links are flagged by browsers, may trigger spam filters, and can expose recipients to security risks. Change all http:// links to https://.
sc_cid Validation Catches all tracking parameter problems: missing sc_cid, empty value, wrong value, duplicate parameter, parameter in path instead of query string, and relative URLs with no hostname. See the sc_cid section for full details. Add or correct the sc_cid parameter on every link.
Duplicate HTML Attributes The same attribute appearing twice on one element — e.g. width="600" width="800". Which value the browser uses is undefined and inconsistent across clients. Remove the duplicate attribute, keeping the correct value.
Duplicate Element IDs Make all id attribute values unique.
Nested Anchor Tags An <a> tag nested inside another <a> tag. This is invalid HTML. Browsers restructure the DOM when they encounter it, often in unexpected ways. Restructure so links are never nested inside other links.
Email File Size Warning Email HTML exceeding Gmail's 102 KB clip threshold. Gmail truncates the email body with a "Message clipped" link, hiding content — including the unsubscribe link — from the recipient. Reduce HTML size: remove commented-out code, trim whitespace, use shorter class names, host large content externally.
Image Policy Violations Images failing any of these requirements: src not from https://explore.redhat.com/, missing alt attribute (null, not just empty), missing width or height, missing border="0". Fix each flagged image attribute. All production images must be hosted on the approved CDN.
Table Layout & Accessibility Tables missing border="0" (prevents default borders in Outlook) or role="presentation" (tells screen readers the table is for layout, not data). Add border="0" role="presentation" to every layout table.
Trademark Formatting Issues The registered trademark symbol (®) in any form other than the exact required markup. See the Trademark section for details. Use only <sup style="line-height:0;">&reg;</sup>.
Nested Trademark Tags <sup> tags incorrectly nested inside each other around the ® symbol — e.g. <sup><sup>®</sup></sup>. Use a single, correctly formatted <sup> tag.
Invalid Background Image Source CSS background images set via background-image: url(...) that are not hosted on https://explore.redhat.com/. Move background images to the approved CDN.

All checks — Warnings

Warnings indicate best-practice violations. The email can technically be sent, but these issues may degrade the recipient experience for some users or email clients.

Check nameWhat it detects & why it matters
Inline CSS RequiredNon-empty <style> blocks in the <head>. Gmail and many mobile clients strip the <style> block entirely, so any styles defined there disappear. All CSS must be applied as inline style="" attributes.
Unsupported Media Elements<video> and <audio> elements. Not supported in the majority of email clients. They are either stripped silently or replaced with a broken placeholder.
Inaccessible LinksAnchor tags with no visible text, no aria-label, and no image with a meaningful alt attribute. Screen readers cannot announce what these links do, making the email inaccessible to blind and visually impaired users.
Empty href AttributesLinks with href="". These resolve to the current page (the email itself) and are almost always a templating error.
Links without target="_blank"External links that do not open in a new tab. When a recipient clicks a link in an email client and the page opens in the same window, it can close or navigate away from the email client, which is disorienting.
Links missing rel="noopener noreferrer"Links with target="_blank" that lack rel="noopener noreferrer". Without this, the opened page gains access to your page via window.opener, a security vulnerability.
Invalid Link ColorLink text colours other than the two approved brand colours: #EE0000 (Red Hat red) and #0066CC (Red Hat blue). Image-only links are exempt from this check.
Links with title="null"The literal string title="null" on a link. This is a common templating bug where a variable that was supposed to contain a title was never populated.
Invalid Font FamilyText rendered in fonts other than the approved brand fonts: Red Hat Text, Red Hat Display, or RedHatText-Regular. Detected via the browser's computed style, which accounts for CSS inheritance.
Font Size Below MinimumText with an inline font size below 11px (in px or pt units). Text this small is unreadable on mobile devices. Note: em and rem units are relative and are not checked.
Low Line HeightBlock-level text elements with a unitless or em line-height below 1.4. Tight line spacing makes text difficult to read, especially on mobile.
Unsupported CSS PropertiesInline style properties not supported by major email clients: display:flex, display:grid, display:inline-flex, display:inline-grid, position:fixed, position:sticky, animation, transition, transform.
CSS !important Usage!important in inline style attributes. Some email clients (particularly older versions of Outlook) may ignore or misinterpret it, causing unintended style overrides.
Broken / Placeholder Image SourcesImages with src pointing to known placeholder or development domains: localhost, via.placeholder.com, picsum.photos, dummyimage.com, and others. These indicate test images that were never replaced with production assets.
Spacer Images DetectedImages used as layout spacers: 1×1 pixel images, or images whose filename contains "spacer", "blank", or "clear.gif". These are an outdated technique. Use CSS padding and margins instead.
Relative src= URLsImage, video, or source elements with relative src attributes (e.g. /images/logo.png or ../assets/photo.jpg). These resolve relative to the email client's rendering context (usually about:blank) and will always produce broken images.
Email Width ViolationsTable, TD, or div elements with an explicit width exceeding 640px. The safe maximum width for email layouts is 640px — wider than this breaks on common mobile screen widths.
Validate "Red Hat" SpacingThe brand name written as one word (RedHat) or with a regular space between the words. Brand guidelines require a non-breaking space (U+00A0, written as &nbsp; in HTML) between "Red" and "Hat" so the name never wraps across a line break.
Placeholder (Dummy) TextLorem ipsum and related placeholder text keywords left in from the template. These include: lorem, ipsum, dolor, amet, consectetur, adipiscing, elit, nullam, aliquam, purus, iaculis, viverra, morbi, sollicitudin, convallis, curabitur, vestibulum.
Extra WhitespaceMultiple consecutive spaces in text content, or leading/trailing spaces in attribute values (e.g. style=" padding: 20px"). These can cause subtle rendering inconsistencies.
Commented-Out CodeHTML comments that appear to contain active code — tags, URLs, or style= attributes. Commented-out code adds file size, may contain outdated tracking URLs, and is a maintenance hazard.

All checks — Info

Info-level checks flag missing recommended elements. These are not errors, but they represent best practices that improve email client compatibility, accessibility, and legal compliance.

Check nameWhat it detects & why it matters
Missing lang AttributeThe <html> element has no lang attribute. Screen readers use the lang attribute to select the correct language for text-to-speech pronunciation. Example fix: <html lang="en">.
Missing <title> TagNo <title> element in the <head>. Some email clients display the title as a label or tab heading. It is also required for accessibility.
Missing <meta charset>No character encoding declaration. Without <meta charset="UTF-8">, special characters (accented letters, em dashes, trademark symbols) may render as garbled characters in some email clients.
Missing Viewport Meta TagNo <meta name="viewport"> tag. Without it, some mobile email clients render the email at desktop width and require the user to zoom in.
Missing Preheader TextNo preheader element detected. A preheader is a short line of hidden text at the top of the email body that appears as the preview text in the inbox list view — the second line of text visible before the email is opened. Its absence means the inbox shows the first line of email content as the preview, which is often the alt text of a spacer image or a navigation link.
Missing Unsubscribe LinkNo text matching common unsubscribe patterns: "unsubscribe", "opt-out", "manage preferences", "email preferences", "manage subscriptions". CAN-SPAM and GDPR require a clear opt-out mechanism in every commercial email.
Missing Physical AddressNo street address or postal code detected in the email body. CAN-SPAM requires that every commercial email include the sender's valid physical address (street address, PO box, or private mailbox).

Understanding sc_cid tracking

The sc_cid (Source Code Campaign ID) is a URL query parameter appended to every outbound link in a Red Hat marketing email. It tells the analytics platform which specific email campaign generated each click, enabling accurate attribution and ROI measurement.

Correct format

https://www.redhat.com/products/rhel?sc_cid=7013a000003SUdXAAW

The auditor checks each link against the sc_cid value you entered at the top of the page and reports six different failure modes:

Failure typeExample URLMeaning
Missinghttps://redhat.com/productsNo sc_cid parameter at all.
Empty?foo=bar&sc_cid&other=1The parameter name is present but has no = sign and no value.
Wrong value?sc_cid=WRONG_VALUEThe parameter is present but the value does not match what you entered.
Duplicate?sc_cid=ABC&sc_cid=ABCThe parameter appears twice. The analytics platform may only read one.
Malformed/path/sc_cid=ABCThe parameter is in the URL path, not the query string.
Relative URL?sc_cid=ABCThe link has no domain — it would resolve to whatever the email client is currently showing (usually nothing).
✅ Exempt links: The following links are excluded from sc_cid checking because they are standard footer links that do not require campaign tracking: the Red Hat privacy policy, contact page, preference centre, and official social media profiles (Facebook, X/Twitter, LinkedIn, YouTube).

Case sensitivity

The parameter name check is case-sensitive. SC_CID= or Sc_Cid= will be flagged as missing. The parameter must be lowercase sc_cid.

Trademark formatting rules

The registered trademark symbol ® must be marked up in a very specific way to prevent it from adding unwanted vertical spacing to the text line it appears on. This is one of the strictest checks in the auditor — only one exact form is accepted.

The only accepted form

Required (PASS) <sup style="line-height:0;">&reg;</sup>

Everything else fails

Fails — literal ® character, not &reg; entity <sup style="line-height:0;">®</sup>

Fails — space after colon in line-height <sup style="line-height: 0;">&reg;</sup>

Fails — no trailing semicolon <sup style="line-height:0">&reg;</sup>

Fails — px unit added <sup style="line-height:0px;">&reg;</sup>

Fails — extra attribute on sup <sup style="line-height:0;" class="tm">&reg;</sup>

Fails — uppercase tag name <SUP style="line-height:0;">&reg;</SUP>

Fails — ® outside any sup tag Red Hat® Enterprise Linux
💡 Why so strict? The DOM-based auditing approach (used for most other checks) cannot enforce this level of precision — the browser decodes &reg;, ®, and the literal ® character to the same Unicode value before any JavaScript sees it. The trademark check scans the raw HTML string before browser parsing, which is the only way to enforce exact encoding and exact attribute formatting.

Disabling a check to make a report look cleaner means the underlying problem goes undetected — and may reach recipients. If a check seems incorrect for your use case, reconfigure its thresholds rather than disabling it.

Refactor tool

The Refactor Code button at the bottom of the left column appears once the audit has found issues. Clicking it automatically applies a set of safe, deterministic fixes to your HTML and displays the corrected code in a modal dialog.

What gets fixed automatically

  • Duplicate attributes — the duplicate attribute is removed, keeping the first occurrence.
  • Insecure links — http:// is upgraded to https://.
  • Missing target="_blank" — added to all external links.
  • Missing rel="noopener noreferrer" — appended to the rel attribute, preserving existing values.
  • Links with title="null" — the title attribute is removed.
  • Image link decoration — text-decoration:none is applied to links wrapping images.
  • Image attributes — hygiene inline styles applied to all images.
  • Table accessibility — missing border="0" and role="presentation" added.
  • sc_cid parameter — wrong, missing, empty, or duplicate parameters corrected to the value you entered.
  • Trademark normalisation — stray ® symbols and incorrectly nested <sup> tags restructured.
  • Red Hat spacing — replaces regular spaces in "Red Hat" with non-breaking spaces.
🚨 Always review the refactored code before using it. The refactor tool makes conservative, mechanical changes. It does not understand your email's intent. Review the diff view (click the "Diff View" tab in the refactor modal) to see exactly what changed, then copy the corrected code into your email platform for further testing.

Diff view

The refactor modal has two tabs: Refactored Code (the full corrected HTML) and Diff View (a line-level comparison showing added lines in green and removed lines in red strikethrough). Use the diff view to quickly understand what the refactorer changed without reading through the entire HTML.

PDF export

Click Export PDF in the summary bar to download a formatted audit report as a PDF file. The PDF is generated entirely in the browser using the jsPDF library and downloads immediately — no popup, no print dialog.

What the PDF contains

  • Report title, generation date, and the sc_cid value that was audited
  • A summary row with counts for Errors, Warnings, Info issues, and Passed checks
  • One section per audit check, colour-coded by severity
  • A table of issues for each failing check, with truncated cell values for long URLs and snippets
  • Page numbers and a footer on every page

Disabled checks are excluded from the PDF. If you have turned off any checks in Settings, they will not appear in the exported report. Enable all checks before exporting a final report for sign-off.

✅ Tip: Export the PDF after fixing all issues and re-running the audit. A clean report showing all checks passed serves as documented evidence of your pre-send QA process.

Live preview

Click Show Preview in the navbar to open a live rendered preview of your email directly below the HTML input area. The preview updates automatically each time the audit re-runs (i.e. each time you change the HTML).

The preview is rendered in a sandboxed iframe — it shows exactly what the email's HTML looks like when parsed by the browser. This is useful for visual verification alongside the audit results.

When you click on a row in a failure table that supports element highlighting, the preview pane opens automatically and draws a red outline around the specific element that caused the failure. This lets you visually locate the problem in the rendered email rather than hunting through the source code.

💡 The live preview renders in your browser engine, not in an email client. It will not show Outlook-specific rendering issues. Use the preview for quick visual checks only; always test in real email clients before sending.

Frequently asked questions

Why does nothing happen when I type the sc_cid?

The HTML input field is locked until a sc_cid value is entered. Once you type any value into the sc_cid field, the HTML textarea becomes active and you can paste or upload your email code.

The audit says a link has the wrong sc_cid value. Is that right?

The auditor compares every link's sc_cid parameter against the value you entered in the sc_cid field at the top. If a link was built for a different campaign (e.g. it uses last month's campaign ID), it will be flagged as "Wrong Value". Check the link URL in the results table to confirm.

Why does my image fail even though it's hosted on explore.redhat.com?

Image policy violations can trigger for multiple reasons at once: even if the source is correct, the check also requires a non-null alt attribute, explicit width and height attributes, and border="0". Expand the failure row to see the specific reason listed for each image.

Can I use ® or ® instead of &reg; for the trademark?

No. Only &reg; is accepted as the trademark content inside the <sup> tag. The reason is that the auditor checks the raw HTML string — not the browser's interpretation of it — to enforce the exact canonical form. The literal ® character and numeric entity forms (®, ®) will fail.

What does "Body Only" mode do differently?

In Body Only mode, the auditor wraps your HTML fragment in a minimal document shell (<!DOCTYPE html><html><head></head><body>…</body></html>) before auditing. This prevents false structural errors from the missing document wrapper. Checks for <meta charset>, viewport meta, <title>, and lang attribute will always trigger in Body Only mode since those belong in the <head>.

The app froze for a few seconds when I dropped a large file. Is that normal?

Yes. For files over 200 KB a status message appears explaining that a large file is being processed. JavaScript in browsers runs on a single thread, so auditing a large document takes exclusive use of the CPU for a short period. The status message and spinner confirm that the app is working, not crashed. The audit will complete and results will appear shortly.

Why is the live preview different from how the email looks in Outlook?

The live preview renders in your browser (Chrome, Firefox, etc.). Outlook uses a completely different rendering engine (Microsoft Word's HTML renderer in desktop versions). CSS that works in your browser may look entirely different in Outlook. The live preview is for quick visual checks only — always test in actual email clients.

My settings disappeared after I cleared my browser cache.

Settings are stored in the browser's localStorage. Clearing browser data (cache, cookies, local storage) removes them. The auditor resets to its default configuration. Re-enter your custom settings in the Settings panel.

TermDefinition
sc_cidSource Code Campaign ID. A URL query parameter appended to outbound links in marketing emails to track campaign attribution in analytics systems.
CAN-SPAMControlling the Assault of Non-Solicited Pornography And Marketing Act (US). Requires commercial emails to include a valid physical address, a clear opt-out mechanism, and honest subject lines, among other requirements.
GDPRGeneral Data Protection Regulation (EU). Requires consent for email marketing and the ability for recipients to withdraw that consent (unsubscribe) at any time.
Inline CSSCSS styles written directly in an element's style="" attribute, rather than in a <style> block or external stylesheet. Required in email because many clients strip external styles.
PreheaderA short line of text at the very top of the email body, typically hidden from view but visible in the inbox preview pane as the second line of text after the subject line.
Sandbox iframeAn isolated browser frame used by the auditor to parse and render the email's HTML without it affecting the auditor's own page. DOM-based checks run inside this frame.
DOMDocument Object Model. The browser's internal representation of an HTML document as a tree of objects. After the browser parses HTML, JavaScript interacts with the DOM rather than the raw text.
EntityAn HTML escape code for characters that have special meaning or are not easily typed. &reg; is the entity for ®, &amp; for &, &nbsp; for a non-breaking space.
Non-breaking spaceA space character (U+00A0, written as &nbsp;) that prevents word-wrapping at that position. Used between "Red" and "Hat" so the brand name never splits across two lines.
LocalStorageA browser API that stores key-value data persistently within the browser, tied to the current domain. Used by the auditor to save Settings and theme preferences between sessions.
MSO conditionalHTML comment syntax (<!--[if mso]>...<![endif]-->) interpreted only by Microsoft Outlook. Used to provide Outlook-specific CSS or layout overrides invisible to other clients.
SeverityA classification of how serious an audit finding is. Three levels: Error (must fix), Warning (should fix), Info (consider fixing).
